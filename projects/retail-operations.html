Operating loop

1. Inventory

Know what is on hand and where replenishment pressure exists.

Translate stock into slot/depth decisions for route equipment.

4. Reporting

Roll current state into operational views that support the next decision.

The Problem

Operational decisions are connected, but software often presents them as separate tasks.

The simulator models a small retail/vending-style environment to show how persistent state can connect everyday operating decisions.

Inventory

Stock has context.

On-hand units, case sizes, target levels, and reorder pressure influence what should happen next.

Procurement

Orders change future state.

Supplier catalogs, draft orders, in-transit status, and receiving decisions are part of the same operating loop.

Execution

Loadout turns planning into action.

Machine slot/depth planning connects available stock with the physical work of servicing a route.

State model

Run → inventory → vendor planning → order → loadout → reporting

The project treats the scenario as a persistent system rather than a collection of disconnected forms. A decision in one area changes what is possible or visible in another.

Why It Matters

It connects my operations background to technical systems work.

The project is useful portfolio evidence because the domain is not abstract to me. I spent years working with inventory, ordering, vendors, sales tracking, staffing, and daily operating problems. The simulator translates that operational understanding into explicit data and system state.
