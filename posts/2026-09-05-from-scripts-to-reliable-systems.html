From Scripts to Reliable Systems: Five Engineering Habits I Now Use

A script can produce the right answer once and still be a weak system. The difference shows up when inputs change, execution stops halfway through, a failure needs to be diagnosed, or another person needs to understand what happened.

The short version

The five habits are simple: define contracts, validate early, make state explicit, design for failure and recovery, and keep consequential decisions reviewable by a person.

1. Define the input and output contract

Before adding automation, I want to know what the workflow accepts, what it must produce, and what “valid” means. That can be a schema, required file set, expected columns, allowed statuses, or a small set of invariants.

This makes debugging much easier because a failure can be classified as an input problem, processing problem, or output problem instead of becoming one vague “it broke” event.

2. Validate before doing expensive work

A workflow should reject bad inputs as close to the boundary as possible. Missing fields, malformed records, duplicate identifiers, impossible states, or inconsistent totals are easier to handle before downstream transformations begin.

Validation is not just defensive programming. It is a communication tool: the system tells the operator what assumption failed.

3. Make state explicit and resumable

If a process can run more than once, it should know what already happened. Import ledgers, status fields, receipts, checkpoints, and persistent identifiers make repeat execution predictable.

This is especially useful for data workflows because accidental duplicate processing can create outputs that look plausible while being wrong.

4. Treat failure and recovery as normal paths

Reliable systems do not assume every run succeeds. They make failures visible through logs, reason codes, quarantine areas, error states, or explicit retry behavior.

The goal is not to eliminate every failure. It is to make the next action obvious and prevent one bad record or interrupted run from silently damaging the rest of the workflow.

5. Keep consequential actions reviewable

Automation is useful, but not every decision should disappear into automation. When an action changes important state, publishes information, sends something externally, or has a meaningful downstream consequence, a review point can be a feature rather than friction.

That principle also improves debugging because the system has a clear boundary between recommendation, approval, and execution.

Transferable lesson

Reliability is mostly about making assumptions visible.

The tools change between analytics, automation, support, and software projects. The habit does not: define what should happen, preserve enough evidence to know what did happen, and make recovery understandable.
